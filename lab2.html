Lab 2: GPIO Device-State Input

Turn physical Raspberry Pi controls into a device-state stream that drives one Overbug player on a PC.

Before you begin

Kernel warning Before starting Lab 2, boot the clean rpi-6.1.y GPIO-lab kernel built in Lab 1's appendix and build against its matching source tree. Verify that uname -r exactly matches the $KREL printed during that build. A Lab 1 kernel or a mismatched build tree may cause module-build or module-load errors.
Teaching API This course intentionally pins Linux 6.1 to demonstrate the deprecated integer-based GPIO API. New production drivers should use the descriptor-based gpiod_* API instead.

This lab assumes you understand:

  • the user-kernel boundary from Lab 1;
  • Linux device files and read();
  • kernel module build, load, and unload commands;
  • active-low GPIO wiring with pull-up resistors.
  • basic socket programming, including IP addresses, port numbers, and the use of socket(), sendto(), and recvfrom();
  • the basic behavior of UDP as a connectionless, best-effort transport protocol.

By the end, you will expose a GPIO device state, transmit it over UDP, and verify it in Overbug.

1. Read GPIO

The driver reads six GPIO inputs, one for each control: UP, DOWN, LEFT, RIGHT, ACTION, and SOLDER, and represents their combined state as one six-bit state mask value. The lab wiring is active-low: pressing a control connects its GPIO line to GND.

Choose GPIO pins

  • Choose six pins labelled GPIO; do not use a 3.3 V, 5 V, or GND pin as a GPIO input.
  • Record each physical header position and its BCM GPIO number before wiring your controls.
  • Configure the same six BCM GPIO numbers in your driver.c module parameters.
  • Connect each input through a physical pull-up resistor; the legacy API used in this lab does not configure the internal bias.
Pin availability Available GPIO functions depend on the Raspberry Pi model, kernel, device-tree configuration, and enabled hardware interfaces. Before wiring, verify that each selected pin is available as a GPIO input and is not reserved for another function.
Wiring safety Use 3.3 V GPIO logic only. Do not connect Raspberry Pi GPIO pins to 5 V.

State mask

Each control corresponds to one bit in the device-state value: 

#define OB_BTN_UP      0x01 // 0b000001
    #define OB_BTN_DOWN    0x02 // 0b000010
    #define OB_BTN_LEFT    0x04 // 0b000100
    #define OB_BTN_RIGHT   0x08 // 0b001000
    #define OB_BTN_ACTION  0x10 // 0b010000
    #define OB_BTN_SOLDER  0x20 // 0b100000

Multiple pressed controls are combined into the same value. For example, UP and ACTION produce 0x01 | 0x10 = 0x11 (0b010001).

2. Expose state (For debugging)

The driver exposes the current device state to user-space programs through /dev/overbug_buttons.

Device-state data flow

Each successful read() from /dev/overbug_buttons returns one ASCII line: 

OBTN XX\n

XX is the two-digit hexadecimal value of the current device-state mask. For example, if UP and ACTION are pressed, the mask is 0x11, so the driver returns: 

OBTN 11\n
  • Each read() obtains and returns the current device state.
  • If the reader buffer is too small for the complete line, the driver returns an error rather than a partial state.

3. Send input

reader.c reads the device state from /dev/overbug_buttons, packages the state in the required OBIN message format, and sends it to server.c over UDP. See Network interface section for the exact packet layout.

Polling

  • reader.c repeats this read-package-send cycle at the rate selected by --hz; the default is 60 Hz.
  • Each OBIN message is sent to UDP port 17666.
  • Lab 2 uses polling. A later extension can replace this with interrupt-driven delivery.

Network interface

The reader converts each sampled OBTN XX line into one UDP input packet for the PC game server.

Reader command

./reader --server <PC_IP> [--device /dev/overbug_buttons] [--port 17666] [--player 1] [--hz 60]

UDP contract

  • Each read-package-send cycle produces one OBIN message, which reader.c sends to the server's UDP port 17666.
  • magic is "OBIN"; it identifies this message as an Overbug input message.
  • Use player_id 1 for Lab 2. The single-player server ignores other IDs.
  • button_mask is the six-bit value parsed from OBTN XX.

Packet layout

struct __attribute__((packed)) ob_input_packet {
    char magic[4];       /* "OBIN" */
    uint8_t player_id;   /* 1 for Lab 2 */
    uint8_t button_mask; /* device state */
};

This definition lives in overbug_protocol.h. Include that header from both reader.c and server.c so both programs always agree on the packet size and field order.

Driver checklist

  • Initialize GPIO: Request each configured BCM GPIO with gpio_request() and configure it as an input with gpio_direction_input().
  • Register the device interface: Register the overbug_buttons misc device so user-space programs can access it through /dev/overbug_buttons.
  • Read and return the device state: In the driver's read() operation, read the six GPIO inputs with gpio_get_value(), encode them into the six-bit state mask, and return the state in the required OBTN XX\n format.
  • Clean up: When the module unloads, unregister the misc device and release every requested GPIO with gpio_free().

Reader checklist

  • Parse the command-line. (server address, device path, port, player ID, and polling rate)
  • Fill the shared OBIN packet fields, then send it with UDP.

Makefile checklist

You must write a Makefile for your submission. It should make the kernel module and user-space reader easy to build and clean.

  • make module builds overbug_buttons.ko through the matching clean 6.1 kernel source tree on the Ubuntu VM.
  • make reader compiles reader.c into the reader program.
  • Run make clean with the same VM kernel-tree arguments to remove module build output; it also removes the reader executable.

Build and run

Cross-compile the kernel module on the Ubuntu VM

The custom kernel installation provides modules but not a /lib/modules/$(uname -r)/build tree on the Pi. Build the module against the same clean 6.1 source directory used to produce the running kernel, then copy the resulting .ko file to the Pi. 

cd Lab2
make KDIR=/path/to/linux-rpi-6.1-gpio \
    ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- module
scp overbug_buttons.ko <pi-user>@<pi-address>:~/Lab2/

On the Raspberry Pi

Load the cross-compiled module, verify one device-state line, then build and start the reader:

cd ~/Lab2
sudo insmod overbug_buttons.ko

make reader
./reader --server <PC_IP> --player 1

The device test should print a line such as OBTN 00. Press a control and run it again to confirm the expected bit changes.

On the PC or Ubuntu VM

Install pygame-ce if it is not already available, then start the display and server:

cd Lab2
gcc -std=c11 -Wall -Wextra -O2 -o server server.c -lm
python3 -m pip install pygame-ce
python3 display.py --host 0.0.0.0 --port 17667

In a second terminal on the same PC or VM:

cd Lab2
./server --input-port 17666 --display-host 127.0.0.1 --display-port 17667

Start the Raspberry Pi reader last. Its physical controls should now move or operate the one Overbug player in the display window.

The on-screen timer stays at 03:00 and the round never ends on its own. This is expected: the Lab 2 baseline does not count the timer down or advance the soldering and inspection progress bars. You add the round timer and timed facilities later, in Lab 4.

Your Makefile targets
